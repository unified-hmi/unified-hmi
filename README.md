# unified-hmi

unified-hmi is a distributed display framework for building multi-display,
multi-node cockpit and cluster user interfaces.
It orchestrates application lifecycles and window layout across a *master* node
and one or more *worker* nodes, and tunnels GPU/Wayland output between nodes
using [RVGPU](https://github.com/unified-hmi/remote-virtio-gpu)-based virtio-GPU
proxies. Clients communicate with the master over gRPC, while master-worker
coordination uses custom TCP protocols (Lifecycle/Layout), and the whole
system is driven by a small set of JSON configuration files.

## Features

- **Distributed app lifecycle** — start, stop, and list applications across
  master and worker nodes.
- **Virtual-screen window management** — place, move, resize, reorder, and
  animate windows across multiple physical displays defined as a single virtual
  screen.
- **Remote GPU / Wayland tunneling** — share rendered output between nodes via
  rvgpu-proxy / rvgpu-renderer.
- **gRPC-first control plane** — a single unified `UHMIService` exposes
  orchestration, app-lifecycle, and window-management operations.

## Architecture

The control plane is layered into three cooperating management domains, exposed
to clients through one unified gRPC service (`UHMIService`):

- **UHMI** (`internal/server/uhmi`) — the orchestration layer and unified
  gRPC facade; combines
- **Lifecycle** (`internal/lifecycle`) — application lifecycle management: spawning app
  processes, environment setup, signal handling, and worker-node connections.
- **Layout** (`internal/layout`) — window/layout management: virtual layers and
  surfaces, positioning, animation, and the rvgpu graphics backend.

Supporting packages: `internal/config` (centralized path resolution via
environment variables, virtual-screen and common-settings parsing), and
`internal/ulog` (logging).

```text
          clients (uhmi-comm, gRPC)
                     │ gRPC
              ┌──────▼───────┐
              │  master node │  UHMIService (UHMI = Lifecycle + Layout)
              └──────┬───────┘
                     │ TCP (Lifecycle/Layout)
          ┌──────────┬──────────┐
     ┌────▼────┐           ┌────▼────┐
     │ worker  │           │ worker  │   app processes
     │         │           │         │   + rvgpu-proxy/rvgpu-renderer
     │         │           │         │   + rvgpu-wlproxy (Wayland bridge)
     └─────────┘           └─────────┘
```

## Related components

unified-hmi builds on a small set of companion projects for GPU/Wayland
tunneling between nodes:

| Component | Role |
|-----------|------|
| [remote-virtio-gpu](https://github.com/unified-hmi/remote-virtio-gpu) | rvgpu-proxy (sender) / rvgpu-renderer (receiver): forwards GPU commands between nodes over virtio-gpu. |
| [virtio-loopback-driver](https://github.com/unified-hmi/virtio-loopback-driver) | Kernel driver exposing `/dev/virtio-lo`, required by rvgpu-proxy before a session can start. |
| [rvgpu-wlproxy](https://github.com/unified-hmi/rvgpu-wlproxy) | Wayland proxy that bridges an app's Wayland client into the virtio-gpu session. |

### Commands

| Command | Role |
|---------|------|
| `uhmi-master-node` | Central gRPC server hosting `UHMIService`; loads configs and coordinates Lifecycle/Layout. |
| `uhmi-worker-node` | Per-node agent that runs app processes and the rvgpu graphics backend. |
| `uhmi-comm` | CLI client that sends gRPC commands (orchestration, app lifecycle, window ops) to the master. |

## Requirements

- Go 1.16 or newer (`make` runs `make mod` to regenerate the untracked
  `go.mod`/`go.sum` for your toolchain and enforces `GOTOOLCHAIN=local`).
- Key dependencies: `google.golang.org/grpc`, `google.golang.org/protobuf`
  (generated by `make mod`).

## Environment setup

Before building unified-hmi itself, set up the remote-virtio-gpu stack on
each participating node:

1. Build and load [virtio-loopback-driver](https://github.com/unified-hmi/virtio-loopback-driver)
   so `/dev/virtio-lo` is available (required by rvgpu-proxy).
2. Build [remote-virtio-gpu](https://github.com/unified-hmi/remote-virtio-gpu)
   (`rvgpu-proxy`, `rvgpu-renderer`) and [rvgpu-wlproxy](https://github.com/unified-hmi/rvgpu-wlproxy),
   and make sure their binaries are on `PATH`.
3. Proceed to [Build](#build) below to build unified-hmi's own commands.

See each project's README for detailed build/install instructions.

## Build

Build and install all commands:

```sh
make            # equivalent to: make install
make install    # build/install the cmd/ binaries only
```

Binaries are installed with `go install` (into the Go bin directory, e.g.
`$GOPATH/bin` or `~/go/bin`). Additional targets:

```sh
make fmt        # gofmt the sources
make lint       # vet/lint the sources
make clean      # remove build artifacts
make doc        # generate package docs
```

You can also build a single command directly, e.g.:

```sh
go build ./cmd/uhmi-master-node
```

## Run

Start the master node, then a worker node on each participating machine:

```sh
uhmi-master-node    # on the master
uhmi-worker-node    # on each worker
```

Drive the running system with the CLI client. Commands are selected with the
`-c` flag (`uhmi-comm -h` lists them all):

```sh
uhmi-comm -c <command> [args...]   # orchestration, app lifecycle, window ops
```

`uhmi-comm` is just a sample client: every command it sends is a call to the
`UHMIService` gRPC API defined in [proto/uhmi.proto](proto/uhmi.proto), so any
application can embed the same orchestration, app-lifecycle, and
window-management operations directly instead of shelling out to `uhmi-comm`.
See [gRPC client samples](#grpc-client-samples) for reference clients to build
from.

### Launch an application

Applications are registered in
[app-list-def.json](example/etc/uhmi-framework/app-list-def.json) (which includes `glmark2`) or, per-app,
in a `<UHMI_APP_DIR>/<appName>/app.json` file. The per-app `app.json` takes
precedence over `app-list-def.json` when both exist.

Launching **with a destination** works with either registration method:

```sh
uhmi-comm -c ListAvailableApps                       # list launchable app names
uhmi-comm -c LaunchApp glmark2 screen0       # launch onto a destination
uhmi-comm -c LaunchApp glmark2 screen0 async # launch without blocking
```

Launching **without a destination** additionally requires a
`<UHMI_APP_DIR>/layout/<appName>/initial_layout.json` that describes the
initial placement. The repository does not include that file for `glmark2`;
create it and, if using per-app registration, `app.json` before running:

```sh
# Example paths for per-app registration and initial layout:
#   $UHMI_APP_DIR/glmark2/app.json
#   $UHMI_APP_DIR/layout/glmark2/initial_layout.json
uhmi-comm -c LaunchApp glmark2                  # layout from initial_layout.json
```

If `initial_layout.json` is absent, `LaunchApp` without a destination
returns an error asking the caller to supply `destName`.

- `destName` (optional) — a placement destination (see `ListDestinations`).
- `async` (optional) — return immediately instead of blocking until the app
  process exits.

### Move an application window

Move a running app's window to a named destination — a virtual display, a
virtual display area, or a built-in sub-area defined in
[virtual-screen-def.json](example/etc/uhmi-framework/virtual-screen-def.json)
(e.g. `screen0`, `screen0_TR`) — with `MoveWindow`:

```sh
uhmi-comm -c ListDestinations                        # list valid destinations
# MoveWindow <appName> <destName> [durationMs]
uhmi-comm -c MoveWindow glmark2 screen0_TR       # default 1000 ms move
uhmi-comm -c MoveWindow glmark2 screen0_TR 500   # 500 ms move
```

- `destName` — a destination name from `ListDestinations`.
- `durationMs` (optional) — animation duration in milliseconds (default `1000`).


## Configuration

Configuration lives under `example/etc/uhmi-framework/` (installed by default to
`/etc/uhmi-framework`). Paths are resolved by `internal/config` and can be
overridden with the `UHMI_CONFIG_DIR`, `UHMI_APP_DIR`, and `UHMI_RUNTIME_DIR`
environment variables.

| File | Purpose |
|------|---------|
| [app-list-def.json](example/etc/uhmi-framework/app-list-def.json) | Declares launchable applications (name, command, environment, startup parameters). |
| [virtual-screen-def.json](example/etc/uhmi-framework/virtual-screen-def.json) | Defines the virtual screen: physical display positions/sizes and drawable areas. |

### Override configuration paths

Set an item-specific environment variable to override one configuration file.
Item-specific paths take precedence; otherwise each file is resolved under
`UHMI_CONFIG_DIR` (default: `/etc/uhmi-framework`).

| File | Environment variable | Read by |
|------|----------------------|---------|
| `app-list-def.json` | `APP_LIST_DEF_PATH` | `uhmi-master-node` only |
| `virtual-screen-def.json` | `VSDPATH` | both nodes |

For example, point the application and virtual-screen definitions at custom
files before launching the master node:

```sh
export APP_LIST_DEF_PATH=/custom/config/app-list-def.json
export VSDPATH=/custom/config/virtual-screen-def.json
uhmi-master-node
```

For a single invocation, command-line flags are an alternative. Both
`uhmi-master-node` and `uhmi-worker-node` accept `-f <path>` to select
`virtual-screen-def.json`. `uhmi-master-node` also accepts `-a <path>` for
`app-list-def.json`.
